# Concord — повторные запросы, звонки и конкурентные действия

Продолжение аудита 16 октября 2026. Все перечисленные сбои воспроизведены автоматическими тестами либо браузерным сценарием до исправления. Дизайн и CSS не менялись: production CSS остаётся `main-5WAF5OHU.css`. Предыдущий отчёт по установке, почте и медиа сохранён в [VERIFICATION-AUDIT-2026-10-16.md](VERIFICATION-AUDIT-2026-10-16.md).

## Исправления

| Сбой | Исправление и проверка |
| --- | --- |
| Повтор POST после обрыва создавал несколько сообщений, упоминаний и уведомлений | `nonce` сохраняется в PostgreSQL с хешем исходного запроса и уникальным индексом по автору/каналу. Конкурирующие повторы получают одно сообщение; изменённое содержимое с тем же ключом возвращает `409 NONCE_CONFLICT`. Тест отправляет четыре параллельных запроса. |
| Повтор сообщения с уже использованным файлом не проходил; ответ мог теряться при ручном повторе | Повтор проверяется до расхода вложений и slowmode. Composer повторно использует ключ того же неудавшегося запроса. Кнопка повтора сохраняет ключ и reply target. Chrome-тест реально сохраняет сообщение на сервере, обрывает HTTP-ответ, повторяет отправку и проверяет ровно одну строку с исходным вложением и ответом. |
| Redis publish падал после COMMIT, но API сообщал о неуспешной отправке | Сохранённое сообщение возвращается успешно; сбой доставки события журналируется отдельно. История остаётся доступной. Это не заменяет гарантированную доставку pub/sub во время аварии Redis. |
| Неверный reply или файл расходовал паузу медленного режима | Сначала выполняется проверка данных. Резерв slowmode снимается при откате SQL только владельцем этого резерва. Повтор уже сохранённого запроса работает и во время паузы; новое сообщение продолжает получать 429. |
| Более старый COMMIT откатывал последние ID канала и автора | Обновления ID монотонны; старое сообщение не стирает более свежий счётчик упоминаний автора. Тест задерживает старую транзакцию после INSERT и фиксирует новую раньше неё. |
| Дублированное gateway-событие дважды считало упоминание | Ограниченная дедупликация учитывает аккаунт, канал и ID. Оптимистическое сообщение также сопоставляется с ответом/историей после неудачной отправки. |
| Несколько вкладок создавали повторные звонки и записи о пропущенном вызове | Один активный ring резервируется через Redis NX. Ответ/отклонение атомарно сравнивает и удаляет конкретный ring. Четыре одновременных отклонения создают одну запись; звонящий не может ответить сам себе. |
| Старое отклонение или таймер скрывал новый звонок в том же DM | У звонка есть ID, события и кнопки передают его. Старые таймеры отменяются; после ready используется оставшийся TTL. Logout освобождает таймеры. Старое завершение без ring ID не скрывает новый входящий вызов. |
| После неудачного подключения к голосу всё равно отправлялся вызов | `voice.join` возвращает результат подключения. Исходящий ring и включение камеры выполняются после успеха. Неудачный ответ на входящий вызов не отправляет ложный accept. Chrome-тест имитирует 503 token endpoint и проверяет отсутствие `call:ring`. |
| Запоздалый read/clear после ready обнулял свежие уведомления | Сервер выдаёт монотонную ревизию, согласованный unread и снимок строк. Мутации сериализуются по пользователю. Клиент не применяет старые счётчики и хранит состояния строк для событий, доставленных в обратном порядке. Есть серверные и клиентские тесты, включая clear до create. |
| Событие во время сборки ready затиралось снимком | Gateway буферизует события до ready и отправляет их после него. Очередь ограничена; события сервера с уже снятой подпиской не воспроизводятся. Реальный WebSocket-тест создаёт уведомление между снимком и отправкой ready. |
| Ошибка ready оставляла частично авторизованный сокет открытым | Ошибка закрывает соединение кодом перезапуска; тайм-аут охватывает полное построение ready. Клиент может переподключиться, сохранив сессию. |
| Одновременный webhook и client join дублировали голосовую историю; старая комната сохраняла участника | Переходы одного пользователя сериализованы. Переключение удаляет старого участника SFU и адресно отключает старую комнату на устройствах. Повторный join идемпотентен; поздний leave старой комнаты сохраняет новую. Запись активной voice session использует атомарный UPSERT. |
| Встречное переключение двух участников могло вызвать SQL deadlock | Обе комнаты блокируются в стабильном порядке до изменения истории. Тест задерживает закрытие исходных voice sessions и одновременно меняет двух пользователей местами; до исправления PostgreSQL возвращал `40P01`. |
| Неуспешный SFU mute отображался как применённое ограничение | При отказе UpdateParticipant выполняется отключение участника. Сохранённое ограничение действует и на следующий join token. При полной недоступности SFU отзыв остаётся best effort, как описано в предыдущем отчёте. |
| Быстрый возврат SPEAK не восстанавливал микрофон | Отменённая публикация проверяет поколение захвата после await и не возвращает устаревший micPub. Если право вернулось, пока отмена завершается, микрофон запускается заново. Воспроизведено и исправлено в Chrome; проверены остановка исходного захвата и последующий возврат живого трека. |
| Одновременный бан и вход оставляли забаненного пользователя участником | Join, invite, ban, unban и удаление участника используют общую блокировку по серверу/пользователю. Бан и удаление membership выполняются в одной транзакции. Регрессия останавливает вход после проверки bans и параллельно выполняет ban. |

## Проверки

- Backend: **81/81**, frontend: **72/72**; TypeScript и production-сборки проходят. Ключ отправки использует `getRandomValues`, поэтому не требует доступного только в secure context `randomUUID`; это отдельно проверено тестом.
- Chrome edge cases: **10/10**, composer: **4/4**, recovery: **11/11**, общие UI E2E: **17/17**, адаптивы: **120 проверок / 16 размеров**. Регистрация, повтор письма, просроченная ссылка, сброс пароля, вход с новым паролем и восстановление загрузки JS прошли без browser errors. WebRTC loopback проверяет реальную передачу тестового аудио.
- H.264: **1920×1080**, **53,23 кадра/с**, первый кадр **345 мс**, медиана задержки картинки **49,2 мс**, p95 **52,2 мс** (177 валидных измерений). Стереоканалы разделены. Полный SFU reconnect восстанавливает живые микрофон, камеру и экран; получатель действительно декодирует новые HD-кадры. Проверка ждёт эти кадры до 15 секунд вместо единственного снимка через 1,2 секунды; критерий HD не снижен.
- Принудительный VP8 у получателя: **640×360**, **54,36 кадра/с**, первый кадр **393 мс**, медиана **46,3 мс**, p95 **49,4 мс** (181 валидное измерение). Это тест совместимости с адаптивным снижением разрешения, не HD-результат.
- Media lifecycle: signaling reconnect, server mute/unmute с ростом переданных audio bytes, сохранение self-mute, смена источника, отмена незавершённых захватов и быстрый повтор камеры/экрана проходят. После отключения захваты завершены и AudioContext остановлены. Production-сборка восстановлена после тестовой инструментированной сборки.
- Тестовые базы PostgreSQL и Redis отделены от пользовательских. UI-прогон использует отдельные порты, потому что старый тестовый процесс уже занимал стандартный QA API.
- Поведение при полном отказе SFU/Redis и реальная сеть между устройствами не превращаются в гарантированные операции благодаря локальному тесту. Проверки физических слабых ПК, второго устройства и WAN остаются отдельной задачей.
- Измерения используют два Chrome-контекста на одном Windows-компьютере, синтетический canvas 1080p60 и тоны 220/880 Гц. Задержка картинки не является измерением голоса mouth-to-ear, реальной игры, WAN или слабого ПК. Обещание отсутствия всех возможных ошибок из этих проверок не следует.

Обезличенные логи и JSON находятся в [results](results): файлы `*-concurrency.*`. Адреса сетевых интерфейсов и приватные значения из media-отчётов исключены перед публикацией.

## Обновление

Нужны миграции `006_message_nonce.sql` и `007_notification_revision.sql`; штатный запуск backend применяет их автоматически. Пользовательские сообщения, аккаунты, файлы и сессии сохраняются. Обновляйте frontend/backend вместе и завершайте старые backend-реплики: они не обновляют ревизии уведомлений. Команды установки и сохранения данных — в [UPGRADING.md](UPGRADING.md).
