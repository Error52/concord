# Публичная версия — 17 октября 2026

Полный стек развёрнут на Linux VPS: PostgreSQL, Redis, backend, LiveKit, coturn, nginx и Caddy. HTTPS проверен обычным Chrome с проверкой цепочки сертификата, без `ignoreHTTPSErrors`. Существующие сервисы хоста сохранены; сайт использует отдельный HTTPS-порт. Внешний адрес и доступ владельца переданы отдельно. Настоящий SMTP не предоставлен: эта установка явно использует ранее согласованную демопочту, доступную только в своём аккаунте.

## Исправлено

- Некорректный HTTP request-target и WebSocket upgrade (`http://[`) завершали backend. Теперь возвращается 400, следующий health-запрос работает в том же процессе.
- Первая публичная регистрация больше не получает админку. Флаг bootstrap отключён по умолчанию в production, существующие администраторы сохранены. Намеренная выдача через CLI попадает в журнал; параллельное снятие прав сохраняет последнего администратора.
- Сбой записи превью, оригинала либо SQL INSERT больше не оставляет файлы без строки в базе.
- Ошибка загрузки истории имеет видимую кнопку повтора. Закреплённое сообщение в личке открывает нужное место. Формы сервера/канала сохраняют данные после 503; повторный Enter не создаёт параллельные запросы. Ошибка настройки 2FA обрабатывается и позволяет повторить действие.
- `/api/ready` проверяет PostgreSQL/Redis с ограничением времени, объединением одновременных проверок и коротким кешем. `/api/health` остаётся отдельной проверкой процесса. Docker и установщик используют readiness.
- nginx сохраняет защитные заголовки также на HTML, assets и 404; Docker DNS позволяет пережить смену IP backend без перезапуска frontend. Runtime обновлён до стабильного nginx 1.30.6.
- coturn 4.18 не принимал старый `--no-tlsv1_1` и перезапускался. После исправления запуска реальная проверка через TURN выявила ещё сбой Docker hairpin: внутренний адрес попадал под правильный запрет частных сетей. LiveKit теперь объявляет оба адреса; релей разрешает только точный адрес SFU и обновляет его через Docker DNS. PostgreSQL/Redis и другие частные адреса не получают исключений. TCP peer relay отключён, транспорт браузер→TURN по TCP поддерживается.
- Логи контейнеров ограничены 10 МБ × 3 файла. Backup публикует только завершённый комплект; ошибка pg_dump не превращается в «успешный» пустой архив. `QUIESCE=1` согласует SQL/локальные uploads и возвращает backend в работу даже после ошибки. Для S3 нужна отдельная копия объектов.

CSS не менялся: production stylesheet остаётся `main-5WAF5OHU.css`.

## Демонстрация через интернет

Источник — синтетический canvas 1920×1080/60 с движением, меткой времени в кадре и разными тестовыми тонами по стереоканалам. Два контекста Chrome на одном Windows-компьютере соединяются через VPS; аппарат захвата и оба реальных независимых клиента здесь не имитируются. После 25 секунд стабилизации полосы снимается десятисекундный интервал. Режим `1080p60` задаёт потолок, адаптация браузера остаётся включённой.

| Путь | Приём | Частота показа | Медиана / p95 картинки | Первый кадр |
|---|---|---:|---:|---:|
| Прямой UDP через VPS | 1920×1080 H.264 | 53,59 кадра/с | 75,4 / 78,0 мс | 1145 мс |
| Принудительный TURN/UDP | 1920×1080 H.264 | 52,99 кадра/с | 136 / 141 мс | 513 мс |
| Принудительный TURN/TCP | 1920×1080 H.264 | 53,04 кадра/с | 124,7 / 127,7 мс | 520 мс |

Во всех трёх прогонах стереоканалы разделены, unhandled browser errors отсутствуют, отключение освобождает захваты и AudioContext. Для TURN проверены одновременно `iceTransportPolicy=relay` и `relayProtocol` выбранного транспорта; в TCP-проверке все UDP TURN URLs исключены. Chrome может показывать локальный peer-reflexive alias выделения TURN вместо типа `relay`.

Начальная короткая проверка Auto снизила поток до 960×540 при ~55 кадрах/с из-за оценки bandwidth. Это нормальная адаптация с приоритетом плавности, но она не проходит HD-порог локального benchmark. Фиксированный потолок 1080p60 после стабилизации дал результаты таблицы. Замеры не гарантируют те же цифры на другом интернете/железе и не являются сравнением с Discord.
