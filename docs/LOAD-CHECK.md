# Ограниченная проверка HTTP и gateway

`scripts/load-check.mjs` измеряет отзывчивость существующей установки. Требуется Node 22 или новее и свежие access tokens отдельных подтверждённых тестовых аккаунтов. Скрипт не регистрирует пользователей, не отправляет письма и сообщения, не меняет роли и не создаёт SFU-подключения. Подключение gateway временно меняет обычный online presence этих аккаунтов.

Сохраните приватный файл вне репозитория, доступный только оператору. Один элемент соответствует одному аккаунту; разные токены того же аккаунта не заменяют отдельных пользователей:

```json
[
  {"accessToken":"FRESH_ACCESS_TOKEN_A","serverId":"SERVER_UUID","channelId":"TEXT_CHANNEL_UUID"},
  {"accessToken":"FRESH_ACCESS_TOKEN_B","serverId":"SERVER_UUID","channelId":"TEXT_CHANNEL_UUID"}
]
```

`serverId` и `channelId` необязательны. Оба пользователя должны иметь доступ к указанным ресурсам. Скрипт читает `/api/ready`, собственный профиль, список серверов и уведомлений; при указанных IDs также последние 50 сообщений и полный снимок сервера. JWT, email, IDs и содержимое ответов не попадают в отчёт. Не публикуйте файл токенов и удалите его после проверки.

Пример запуска из корня проекта в Linux/macOS:

```bash
BASE_URL=https://chat.example.com \
LOAD_ALLOW_PUBLIC=1 \
LOAD_USERS_FILE=/private/concord-load-users.json \
LOAD_OUT=/private/concord-load-results.json \
node scripts/load-check.mjs
```

`BASE_URL` — origin, включая отдельный HTTPS-порт при необходимости. Для адресов вне loopback требуется явный `LOAD_ALLOW_PUBLIC=1`. Проверка TLS остаётся включённой. Без `LOAD_USERS_FILE` измеряется только readiness; это не проверка работоспособности пользовательских функций.

| Ступень | Предлагаемая HTTP частота | Максимум запросов в работе | Gateway соединения |
|---|---:|---:|---:|
| 1 | 2 запроса/с | 1 | 1 |
| 2 | 8 запросов/с | 4 | 4 |
| 3 | 20 запросов/с | 8 | 8 |

Каждая ступень длится 15 секунд. Соединений не больше четырёх на аккаунт; два аккаунта дают восемь соединений, но это всё ещё два пользователя. Авторизация открывается пакетами по два соединения перед HTTP-частью ступени; `connectToReady` относится к этому разогреву. Heartbeat измеряется уже одновременно с HTTP-нагрузкой: раз в две секунды, с одним запросом в работе на сокет. При четырёх соединениях на аккаунт это остаётся ниже штатного лимита 120 gateway операций за 10 секунд.

Допустимые настройки: `LOAD_STAGE_SECONDS=1..30`, `LOAD_MAX_REQUESTS=1..1000`, `LOAD_MAX_SOCKETS=0..20` (таблица ограничивает фактическую ступень восемью), `LOAD_TIMEOUT_MS=250..10000`. Общие пределы: 180 секунд, 1000 HTTP запросов, 32 МиБ прочитанных HTTP данных и 2 МиБ на ответ. Для потоковых ответов уже находящиеся в работе запросы могут завершиться после достижения общего лимита. HTTP 429 останавливает тест сразу; 401/403 указывают на неверный fixture, три прочих ошибки также останавливают тест. Настройки сервера и rate limits не ослабляются.

При достижении лимита параллельности новые временные слоты пропускаются и записываются в `skippedBusySlots`. Поэтому отчёт показывает предлагаемую и фактическую частоту, число завершений, статусы, ошибки, HTTP p50/p95 с чтением тела, время до gateway `ready` и RTT heartbeat. Большое число пропусков означает, что ступень не выдержана, даже если немногочисленные успешные ответы имеют низкий p95. Малое число образцов не даёт устойчивую оценку хвоста задержек.

Это проверка умеренной нагрузки. Она не устанавливает максимальную вместимость сервера и не проверяет число одновременных медиапотоков. Для оценки демонстрации отдельно запустите `frontend/test/media-benchmark.mjs` с двумя браузерными контекстами. Повтор той же синтетической сцены во время согласованной ступени HTTP/gateway позволяет сравнить FPS, задержку кадра, битрейт и потери с ненагруженным запуском. Не запускайте одновременно CPU-тяжёлые сборки и браузерные тесты на генераторе нагрузки: их нагрузка исказит результат.

Локальная проверка инструмента без публичного трафика:

```bash
node --test test/load-check.test.mjs
```
