# Регистрация и исправления — 13 октября 2026

Регистрация теперь проходит через подтверждение почты. В установленной Windows-копии приложение доступно на http://localhost:5173, локальная почта — на http://localhost:58025. Письма остаются на этом компьютере. Для Docker dev-профиля адрес ящика — http://localhost:8025.

## Путь пользователя

1. Имя пользователя, email, пароль и его повтор; необязательные аватар/баннер/оформление профиля.
2. Аккаунт и профиль создаются в одной транзакции, пользователь получает сеанс для завершения регистрации.
3. Пока email не подтверждён, доступна страница ожидания, выход и загрузка собственных изображений. Обычные API и gateway не допускают чат, серверы и голос.
4. Письмо содержит ссылку на 24 часа. GET открывает страницу; подтверждение происходит только после кнопки и POST. Email-сканер, просто открывший ссылку, не активирует аккаунт.
5. Повторная отправка доступна не чаще раза в минуту, с дополнительным почасовым лимитом. Предыдущая ссылка отзывается. Повторное открытие уже подтверждённой актуальной ссылки безопасно.
6. При подтверждении в том же аккаунте клиент получает новый access token и открывает приложение. В другом браузере подтверждение не выдаёт сессию автоматически: нужен обычный вход.

Существующие аккаунты сохранены и переведены в доверенное состояние миграцией 003; новая проверка не блокирует старых пользователей. Это совместимость с прежней регистрацией, а не ретроспективная проверка владения всеми старыми адресами. Демо-пользователи seed создаются доверенными. `REQUIRE_EMAIL_VERIFICATION=true` — значение по умолчанию; фронтенд не является единственным местом ограничения.

## Письма

Отправка вынесена в transactional outbox: создание аккаунта не ждёт SMTP. Один worker использует блокировки строк с SKIP LOCKED; ошибка остаётся в очереди с экспоненциальной паузой, максимум 8 попыток. Гарантия at least once: при падении процесса после принятия письма SMTP возможно повторное письмо. Ссылки проверяются сервером. Очередь и её содержимое приватны и не включаются в передаваемый архив.

Проверен Mailpit 1.31.5 из [официального выпуска](https://github.com/axllent/mailpit/releases/tag/v1.31.5); Windows-архив совпал с опубликованной SHA-256 `9637e21c02b33185fe69268ba05317152a5d8ac7877115e8a70e29b7e199e8dc`. Почтовый клиент больше не теряет раннее SMTP greeting, понимает разделённые многострочные ответы и правильно завершает ожидание при закрытии/ошибке соединения. Добавлены `SMTP_TLS` для implicit TLS и `SMTP_STARTTLS` для upgrade; настоящий внешний SMTP/TLS в этой среде не проверялся.

Для доставки настоящих писем настроить SMTP_HOST/PORT/USER/PASSWORD, TLS/STARTTLS и MAIL_FROM в .env. Локальный ящик не пересылает письма наружу. Native Windows запуск уже настроен; Docker и macOS/Linux launcher требуют проверки на соответствующей машине.

## Найденные и исправленные ошибки

- Конкурирующие первые регистрации могли создать двух автоматических администраторов: решение теперь сериализовано advisory lock. Дубли email/username, прошедшие pre-check одновременно, возвращают правильную ошибку поля вместо общего CONFLICT.
- Одновременный refresh в разных вкладках мог удалить новую shared cookie. Теперь запросы получают одинаковую ротацию в коротком окне, ответ 409 не очищает чужую новую cookie. Временная сеть/503/429 не вызывает принудительный logout.
- Logout и смена/сброс пароля раньше могли оставить действующие access tokens от уже ротированных sessions. Теперь отзыв охватывает соответствующие семейства и старые токены; user-scoped lock упорядочивает refresh, создание сессии и изменение пароля.
- Password-reset token потреблялся отдельно от изменения пароля: два параллельных запроса могли оба принять ссылку. Теперь потребление атомарно; ссылка принимается один раз. Pending MFA-ticket становится недействителен после смены пароля; вход не создаёт сессию с уже сменённым паролем.
- Анонимный logout по cookie теперь проверяет секрет, а не только ID. Неверный UUID в refresh cookie даёт 401, а не ошибку SQL.
- Ссылка сброса пароля теперь открывает форму и при уже активном входе. После сброса сеансы завершаются, возможен вход с новым паролем.
- Blob URL предпросмотра аватара/баннера освобождается при смене файла и выходе из регистрации. Аватар загружается до перехода на страницу подтверждения, пользовательские данные обновляются после загрузки.
- Некорректная percent-encoding URL больше не завершает локальный frontend server; выход из каталога запрещён, отсутствующий JS chunk возвращает 404. После сбоя загрузки модуля пользователь видит повтор загрузки, сессия сохраняется.

## Быстродействие без смены дизайна

Гость загружает только вход/регистрацию и общие зависимости. AppShell и большой LiveKit chunk загружаются после входа. Замер Resource Timing в свежем Chrome-контексте: около **295 КБ JS** вместо предыдущего монолитного ~1,18 МБ, примерно на 75% меньше JS до входа. Это уменьшение первоначального объёма, не уменьшение полного приложения и не гарантия ускорения на столько же процентов. Повторная загрузка Shell после сетевой ошибки проверена в браузере.

CSS остался `main-TZFOKFC5.css`; цвета, шрифты и оформление сохранены. Новые шаги используют существующие auth-card/input/button/pill стили. Media policy, качество кодирования и механизм адаптации демки сохраняются; после изменения сборки заново пройдены реальная доставка stereo/видео и lifecycle-сценарии.

## Запуск тестов

Из frontend против отдельного seeded стека:

```powershell
$env:BASE_URL='http://localhost:8080'
$env:MAILBOX_URL='http://localhost:8025'
pnpm test:auth
pnpm test:e2e
pnpm test:responsive
pnpm test:media
```

Для native QA здесь использованы BASE_URL=http://localhost:5180 и MAILBOX_URL=http://localhost:58026. Только loopback mailbox допустим в тестовом helper. Auth-flow выдерживает настоящую минутную паузу перед resend. Не запускать эти тесты на пользовательском production: они создают аккаунты и меняют пароли своих тестовых аккаунтов. При повторных прогонах на одном IP действует лимит регистрации 5/час — использовать чистую изолированную среду или сбрасывать только её rate-limit ключи, не ослабляя production лимиты.

Серверные тесты — `node scripts/dev.mjs test-api`, frontend unit — `pnpm test`. Exact dependency versions и frozen lockfiles проверены. Новые тесты проверяют SMTP, concurrent registration/refresh/reset, session revocation, cooldown/expiry, реальные локальные письма, загрузку аватара, освобождение preview URL, восстановление chunk и malformed URL.
